# Glossary

Canonical terminology for the ios-agent project. When a term is defined here, use the definition here. If you need to introduce a new term, add it to this file in the same PR.

---

## Conversion modes

The three output modes the converter targets. The MVP supports **Wrap** only (see `mvp-scope.md`); Bridge and Port are deferred to later phases. These names supersede the older labels "wrapper," "semi-native hybrid," and "fully native" — those terms are deprecated in user-facing materials.

### Wrap

A Capacitor-based iOS host project that loads the developer's web app inside a WKWebView, with App Store compliance scaffolding generated alongside. The native shell adds value through native features (push notifications, biometrics, share sheet, camera, deep links) — without those, Apple Guideline 4.2 will reject the submission.

- **Source archetype:** Web codebases only
- **Phase:** 1 (MVP)
- **Replaces the term:** "WKWebView wrapper"

### Bridge

A native iOS shell that contains both web screens (loaded in WKWebView) and native SwiftUI screens. The intended use is progressive migration — start with most screens loaded in the WebView, then replace screens with native implementations one by one. Routing decisions are made per-route, often via a `TabView` or `NavigationStack` that mixes both view kinds.

- **Source archetype:** Web codebases only (in the MVP horizon)
- **Phase:** 3
- **Replaces the term:** "semi-native hybrid"

### Port

A fully native Swift/SwiftUI iOS app produced by transpiling source to a native code structure. Scope is intentionally narrow at first (CRUD, simple forms) because automatic UI translation from web/Android to SwiftUI does not exist as a solved problem.

- **Source archetype:** Phase 2 starts with Kotlin/Java logic-only ports (developer authors UI). Full Port-mode app generation is Phase 4.
- **Phase:** 4 (full app); Phase 2 for logic-only Swift Package output
- **Replaces the term:** "fully native"

## Source archetypes

Categories of input the converter recognises. Defined in `config/compatibility-matrix.yaml`.

- **Web** — HTML/CSS/JS/TS front-end source or built front-end bundles (Vite, Next.js static export, Astro, etc.). MVP-supported source.
- **Java** — Java source for logic-only transpilation via J2ObjC. Phase 2.
- **Kotlin** — Kotlin source for logic-only transpilation via Skip / KMM. Phase 2.
- **TypeScript (logic only)** — Server-side or shared TS libraries (no JSX/UI). Distinct from Web — Web embeds TS as WebView content rather than transpiling it. Phase 5.
- **Python** — Reserved for LLM-assisted, manual-review-required mode. Phase 5.
- **Objective-C** — Not a transpilation target; Swift interops natively.

## Architecture decisions

- **ADR** — Architecture Decision Record. Single-purpose document that fixes a binding decision. Numbered sequentially under `docs/adr/`. Once accepted, an ADR can only be replaced by a superseding ADR — see `docs/adr/0001-tooling-stack.md` for the format.
- **ADR 0001 — Tooling Stack** — Binds the project to specific tools (Capacitor, tree-sitter, swift-syntax, XcodeGen, J2ObjC, Skip, …). Forbids in-house reimplementation of those layers without a superseding ADR.

## Tooling and infrastructure terms

- **Compatibility matrix** — `config/compatibility-matrix.yaml`. The data file that gates which `(source, target)` combinations the tool will accept. The CLI consults it before starting any conversion.
- **MVP scope document** — `docs/mvp-scope.md`. The authoritative reference for what is and is not in scope for the MVP. When the matrix and the scope doc disagree, the scope doc wins until updated.
- **`ios-conversion` branch** — The default branch the converter writes its output to. Configurable. Low-confidence runs are written to a `Requires more review/` prefixed branch instead.
- **Pre-flight scanner** — The compliance checker that runs before output is marked ship-ready. Builds on the API-usage scanner (Tier 1 Step 6).
- **Three-layer report** — Conversion output structured as Layer A (Blockers), Layer B (Manual review), Layer C (Learnings). Defined in Tier 1 Step 7.
- **Wrap-mode minimum-functionality enforcement** — The native-feature density check that protects against Guideline 4.2 rejections. Counts native integrations (push, biometrics, share sheet, etc.) and warns when too few are present.

## Apple App Store terms (used throughout)

- **Privacy manifest** — `PrivacyInfo.xcprivacy`. Mandatory file declaring required-reason API usage, third-party SDK data collection, and tracking domains. Auto-generated by the tool.
- **Required-reason API** — An Apple-defined API whose usage requires a declared reason in the privacy manifest. List is versioned by Apple and tracked in `config/apple-required-reason-apis.yaml` (Tier 1 Step 6).
- **ATS** — App Transport Security. The default `Info.plist`-driven HTTPS enforcement. Disabling it requires per-domain exceptions and reviewer scrutiny.
- **ATT** — App Tracking Transparency. The runtime prompt required for cross-app tracking, plus the `NSUserTrackingUsageDescription` string.
- **SIWA** — Sign in with Apple. Required (Guideline 4.8) when the app offers third-party social login.
- **Guideline 4.2** — "Minimum Functionality." The most common reason Wrap-mode submissions are rejected.
- **Guideline 4.7 / 2.5.2** — Restrictions on downloading executable code at runtime. Constrains JS hot-update patterns.

## Versioning

- **rev N** — A revision of the conversion output committed to the conversion branch. Each conversion run produces a new revision; the prior revision remains in the branch's git history.
- **Confidence score** — A per-symbol scalar produced by the converter, aggregated up to per-file and per-project. Below-threshold runs are routed to the `Requires more review/` branch.
