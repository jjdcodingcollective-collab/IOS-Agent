# Plan: GitHub Round-Trip (Wrapper Feature)

## Summary

A future paid feature: the user gives the wrapper a GitHub repo URL, the
wrapper clones it, runs the converter, and pushes the generated Swift
project as a new branch in the **same** repo so the user can review the TS↔
Swift diff in a single PR.

This is **wrapper-only** — the CLI stays clean and scriptable, but does not
clone or push. All git/GitHub orchestration lives in the conversational
wrapper (Surface 2 in `agent-interaction-design.md`).

## Decisions (locked)

| Question | Decision |
|---|---|
| Same repo or sibling? | **Same repo, new branch** |
| CLI or wrapper? | **Wrapper only** (future paid product surface) |
| Default branch name | `ios-conversion` — user can override |
| Branch already exists? | **Copy and amend** — re-runs commit on top with `rev 2`, `rev 3`, ... |
| Re-runs strategy | **Fresh commit** per run, message carries confidence score + update notes |
| Validation failure blocks push? | **No** — push anyway, prefix branch with `Requires-more-review/` if validation fails |

## User flow

```
User (chat): "Convert github.com/acme/web-app to iOS"
  │
  ▼
Wrapper:
  1. Confirm scope: "I'll clone acme/web-app, convert it, and push to a new
     branch 'ios-conversion'. Continue?"
  2. Clone repo to workspace/<repo>-src
  3. Run CLI: python -m converter.run <src> --output workspace/<repo>-ios
  4. Inspect generation-summary.md → extract avg confidence, file count, TODO count
  5. Determine branch name:
       - first run: "ios-conversion" (or user-supplied)
       - re-runs: same branch, append "rev N" to commit message
       - validation failed: prefix branch as "Requires-more-review/ios-conversion"
  6. Create branch (or check out existing one)
  7. Copy generated Swift project to repo root, replacing prior generated files
  8. Commit with structured message (template below)
  9. Push branch to origin
  10. (Optional) gh pr create with generation-summary.md as body
  11. Return PR/branch URL to the user
```

## Branch naming rules

- Default: `ios-conversion`
- User override: any valid git branch name (validated against
  `git check-ref-format`)
- If validation reports errors: prepend `Requires-more-review/` →
  `Requires-more-review/ios-conversion`. The slash is intentional —
  GitHub renders it as a folder, making review-required branches easy to
  spot in the branch picker.
- The "needs review" prefix is **dropped automatically** on the next
  successful (clean validation) run.

## Commit message template

```
ios: auto-conversion rev {N}

Confidence: {avg}% avg ({high} HIGH / {med} MEDIUM / {low} LOW)
Files: {count} converted, {todo_count} TODOs
Validation: {pass}/{total} pass

Update notes:
{update_notes}

Generated by ios-agent v{version} from {source_sha}
```

- `{N}` increments per run (read from prior commit messages on the branch;
  starts at 1 if branch is new)
- `{update_notes}` describes what changed *since the last revision* — diff
  the new and old `generation-summary.md` confidence tables, surface
  files whose scores moved by ≥10%, new TODOs added/resolved, validation
  delta. Empty for rev 1.
- `{source_sha}` is the upstream HEAD when conversion ran, so users can
  trace which TS commit produced this Swift output.

## Scope of this BUILD

### In scope
- Git operations: clone, branch, commit, push
- Branch naming logic (default, override, "needs review" prefix)
- Revision counter and update-notes synthesis from prior summary
- Wrapper command surface: `convert <github-url>` with optional flags
- Confirmation prompt before any push (irreversible action — confirm per
  CLAUDE.md rules)

### Out of scope (later BUILDs)
- PR creation/auto-merge (the wrapper just pushes; user opens the PR)
- Webhook-driven re-conversion when TS source updates
- Per-file approve/reject workflow
- Billing / paid-feature gating (this is the technical foundation, not
  the commerce layer)
- Sibling-repo mode

## Implementation phases

**Phase 1 — Local round-trip (no GitHub yet)** — ✅ shipped
- Wrapper command: `python -m wrapper convert <local-path>` → runs CLI,
  parses reports, prints triage summary
- Modules: `wrapper/orchestrator.py`, `wrapper/triage.py`, `wrapper/__main__.py`

**Phase 2 — Git operations against a local clone** — ✅ shipped
- Wrapper command: `python -m wrapper convert-from-github <github-url>` →
  clone, convert, commit on a local branch, **no push**
- Implements: branch validation + `git check-ref-format`, protected-branch
  refusal (`main`/`master`/`develop`/`trunk`/`release`),
  `Requires-more-review/` prefix on low-confidence runs (avg < 60% or
  validation errors), revision counter, update-notes diff comparing
  prior vs current `generation-summary.md`, structured commit message
  including upstream `source_sha`, bot identity to avoid posing as the user.
- Validated end-to-end against `the-survival-bible` monorepo via
  `--source-subdir apps/mobile` (42 files, 50/50 validator pass after
  arrow-leak fix, branch `Requires-more-review/ios-conversion` rev 4).
- Module: `wrapper/git_ops.py`

**Phase 3 — Push + branch lifecycle** — ✅ shipped
- `--push` and `--no-push` mutually-exclusive flags on `convert-from-github`;
  default is to prompt after the local commit has landed.
- `--yes` implies `--push` (skip-all-prompts), unless explicitly overridden
  by `--no-push`.
- `push_branch(repo_path, branch, remote='origin')` in `wrapper/git_ops.py`:
  plain `git push --set-upstream`, never `--force`, never `--force-with-lease`.
- Hard refusal at push time if the branch is in `PROTECTED_BRANCHES`
  (`main`/`master`/`develop`/`trunk`/`release`); the prefixed
  `Requires-more-review/<branch>` form is allowed because the head ref no
  longer matches a protected name.
- Read-only fallback: if the remote isn't configured or push fails (missing
  credentials, non-fast-forward, network), the function returns
  `PushInfo(pushed=False, error=...)` rather than raising. The CLI prints
  the error, the local branch stays put, and tells the user the exact
  `git push -u` command to retry by hand.
- Re-runs on a stale branch are deliberately left alone — see "Open
  questions" below; we never rebase the user's history.

Out of scope for Phase 3 (covered by Phase 5):
- `--open-pr` / `gh pr create` — no PR creation yet.
- Webhook-driven re-conversion — not part of the manual surface.

**Phase 4 — Conversational polish** — ✅ shipped
- Pre-flight: `wrapper/repo_metadata.py` parses GitHub URLs (HTTPS / SSH /
  scheme-less / with `.git`), fetches `/repos/{owner}/{repo}`, and renders
  a single-line "About:" banner: `acme/web-app · public · TypeScript ·
  default branch 'main' · last push 2 days ago · 142 stars · 31 open
  issues/PRs`. Auth resolves via `gh auth token` → `GITHUB_TOKEN` → anon.
  Soft-fails on every error path (network down, non-GitHub URL, 404,
  rate-limit) so the conversion never blocks on metadata.
- Post-flight: `wrapper/post_flight.py` renders a copy-pasteable
  `gh pr create` command (with `--body-file
  .ios-conversion/generation-summary.md`) and a fallback
  `…/compare/<base>...<head>?expand=1` URL for users without `gh`
  installed. The default base branch comes from the metadata fetch when
  available, else `"main"`.
- Educational mode: `wrapper/explainer.py` prints a short "What's on this
  branch" block between the local commit summary and the push prompt.
  Two flavours — clean validation runs vs `Requires-more-review/`
  prefixed runs.
- `--brief` flag on both `convert` and `convert-from-github` suppresses
  the metadata banner and the explainer block. The post-flight PR
  command always prints because it's the actionable output.
- Tests: 57 unit tests across `wrapper/tests/test_repo_metadata.py` and
  `wrapper/tests/test_post_flight.py`. No network calls in tests. Run
  with `python3 -m unittest discover -s wrapper`.

**Phase 5 — Optional PR creation** — ✅ shipped
- `--open-pr` flag on `convert-from-github` → invokes `gh pr create`
  with the same `(base, head, title, body-file)` tuple Phase 4 prints.
  Off by default.
- `wrapper/pr_ops.py`: `gh_available()` checks `which gh` + `gh auth status`,
  returning a hint when missing (`brew install gh` / `gh auth login`).
  `open_pr(repo_path, base, head, title, body_path)` runs `gh pr create`
  from inside the clone, parses the resulting `pull/<n>` URL out of
  stdout, and returns a `PrInfo(opened, url, error)`.
- `--no-push --open-pr` is rejected at the argparse layer (incoherent —
  no branch to PR).
- Existing-PR collision (`a pull request for branch X already exists`)
  surfaces verbatim plus the hint that the wrapper does not update PR
  descriptions on re-runs.
- Read-only fallback preserved: if push fails, `--open-pr` is never
  reached. The conversion + local commit always survive.
- Tests: 15 new unit tests in `wrapper/tests/test_pr_ops.py` cover URL
  extraction (alone / with preamble / multiple matches / blank / no URL),
  `gh_available()` (not installed / unauthenticated / OK), and
  `open_pr()` (success, existing-PR error, body-file inclusion/omission,
  cwd respected, success-without-URL, timeout). No real `gh` invocations.

## Wrapper surface (delivered through Phase 3)

```
python -m wrapper convert <source-dir>
    [--output PATH]            default: workspace/<name>-ios
    [--app-name NAME]          default: MyApp
    [--no-validate]
    [--yes]

python -m wrapper convert-from-github <github-url>
    [--branch NAME]            default: ios-conversion
    [--source-subdir PATH]     monorepo subdirectory (e.g. apps/mobile)
    [--workdir PATH]           clone destination root
    [--output PATH]
    [--app-name NAME]
    [--depth N]                shallow clone
    [--reuse-clone]            don't re-clone if dest already exists
    [--no-validate]
    [--yes]                    skip prompts; implies --push
    [--push | --no-push]       Phase 3; default is to prompt after commit
    [--brief]                  Phase 4; suppress metadata banner + explainer
    [--open-pr]                Phase 5; opt-in `gh pr create` after successful push
```

## Wrapper command surface (proposed)

```
convert <github-url>
    [--branch <name>]          default: ios-conversion
    [--app-name <name>]        default: derived from repo name (PascalCase)
    [--push | --no-push]       default: prompt
    [--open-pr]                default: false
    [--strict]                 fail (non-zero exit) if validation has errors
```

Examples:
```
convert github.com/acme/web-app
convert github.com/acme/web-app --branch ios/v1 --app-name AcmeMobile
convert github.com/acme/web-app --push --open-pr
```

## Safety rails (CLAUDE.md "executing actions with care")

1. **Always confirm before push.** First push of a new branch and every
   re-run prompts the user. `--push` skips the prompt only when explicitly
   set; CI environments must opt in.
2. **Never force-push.** Re-runs use fresh commits, not `git push --force`.
   If a user wants to rewrite history, they do it themselves outside the
   wrapper.
3. **Never push to `main`/`master`.** Hard-coded refusal even if a user
   passes `--branch main`.
4. **Never delete branches.** The wrapper only creates and updates.
5. **Read-only fallback.** If push credentials are missing, the wrapper
   completes the local clone + convert + commit and prints the local
   branch path so the user can push manually.

## Open questions (resolved through Phase 3)

- **Re-run on a stale branch:** ✅ resolved — leave alone. The wrapper
  never rebases or force-pushes; the user merges/rebases manually with
  their preferred strategy. The conversion branch always branches off
  the upstream default at conversion time, so a stale base is the user's
  call to fix.
- **Monorepo support:** ✅ resolved in Phase 2 — `--source-subdir
  apps/mobile` (validated against `the-survival-bible`).
- **Private repos with submodules:** still out of scope for v1; the
  wrapper does not pass `--recurse-submodules` to clone. Document and
  fail fast if a user hits it.

## Notes

- This plan stays inside the wrapper because the CLI must remain a pure
  function (TS source dir → Swift project) for testability and CI use.
- The `Requires-more-review/` branch prefix is a UX trick, not a
  technical mechanism — git treats it as an ordinary branch name with a
  slash. Users will see two folders in their branch picker:
  `ios-conversion` and `Requires-more-review/`. Worth A/B testing later.
- This becomes the headline feature of the paid wrapper: "point us at
  your repo, get an iOS PR." Worth treating Phase 4 (the conversational
  polish) as the differentiator, not the git plumbing.
